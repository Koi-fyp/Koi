## M13 — Modal redirect and cold-start compatibility (October 17, 2026)

### Verified Modal behavior

- Inspected `origin/feat/exercise-director-modal` at `4b014ba220898c052f125b8bcc2e6e2cae18a2aa`: `deploy/modal/chat_app.py`, `chat_core.py`, `test_chat_v11.py`, `tools/auth_check.py`, and `tools/wait_ready.py`. The chat app configures `@app.cls(timeout=600, scaledown_window=300)`; `chat_core.py` installs app-level CORS middleware and serves `GET /health` returning `{"status":"ok"}` without calling its Firebase-token auth function. The backend test calls `/health` with no Authorization header. This conflicts with the proposed client contract's claim that `/health` is authenticated; no backend files were changed.
- Modal's official request-timeout documentation says that after a Web Function's 150-second HTTP window it returns a 303 to the original URL with a request-specific query parameter. Fetching that result URL does not trigger the original request again; it blocks until the result is ready. It documents a 20-redirect browser limit and explicitly warns that these proxy-generated redirects do not work for requests requiring CORS because the redirect response lacks CORS headers. Source: https://modal.com/docs/guide/webhook-timeouts. The Modal blog also describes the 150-second request-specific 303: https://modal.com/blog/serverless-http.
- The published Modal Python clients configure a high redirect limit and rely on urllib to follow the same-URL 303; that is source evidence, not evidence that cross-origin browser fetch can read the redirect. The official Fetch Standard returns opaque manual redirects for a cross-origin browser request and removes Authorization if an automatic redirect changes origin: https://fetch.spec.whatwg.org/#http-redirect-fetch.

### Web implementation and limits

- `jsonChatTransport.ts` now uses a 600-second bounded request deadline aligned with the published chat Function's 600-second timeout. It follows only visible 303 responses whose target retains the exact configured API origin and chat/health path; the 303 follow-up is GET, body is removed, and the request-specific query is retained. It never repeats the POST, permits at most 20 redirects, and carries the Bearer header only to the validated same-origin/path result URL. Untrusted, malformed, opaque, unsupported, or excessive redirects fail closed. SSE parsing and event delivery begin only after the final response and are otherwise unchanged; timeout, caller abort, and reader cleanup cover the redirect chain.
- Added `probeChatHealth()` and `chatHealthEndpoint()` for an explicit bounded GET probe. This helper is not automatically called on chat mount and a successful health response is not treated as proof that a later chat request will be warm. No Firebase token is sent to `/health`, following the inspected implementation and test; Ahmad should resolve the documentation mismatch.
- Deterministic local tests verify ordinary SSE, one authenticated POST followed by one same-origin GET to a synthetic request-result URL, no POST replay, untrusted/opaque redirect rejection before any follow-up, the 20-redirect bound, timeout, cancellation during the redirected GET, missing terminal `done`, and GET `/health` request shape. The synthetic query parameter is only a test fixture; the production code does not invent its name.
- Important deployment limitation: a browser request from the Next.js origin to an external Modal origin requires CORS. The documented Modal proxy 303 lacks CORS headers, so a browser's cross-origin `fetch` cannot expose that 303 for the safe manual-follow logic. The code therefore fails clearly on an opaque redirect rather than attempting to follow an uninspectable destination. This implementation supports same-origin or otherwise CORS-visible Modal redirects, but it does not remove Modal's documented cross-origin CORS blocker. Resolving that requires an approved same-origin relay/proxy architecture or a Modal-supported CORS response change; neither was implemented here.
