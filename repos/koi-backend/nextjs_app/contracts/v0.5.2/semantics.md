# WEB-3 semantics

Base 0.5.0 and 0.5.1 semantics remain applicable. Server-registered accounts, verification records, active organization ownership and relationship records are the authorities. Profile fields never confer authorization. All routes authenticate revoked-token-aware Firebase identity and return private/no-store responses.

- Directory reads require registered General capability. Every returned profile is rechecked against verified active practice authority. Discoverability and accepting applications are distinct. Profile writes use expected revision and idempotency receipts; new applications check the current profile within their transaction. Search operates on explicitly labelled loaded directory pages; further pages can be loaded. No anonymous directory reads.
- Human messages are immutable, scoped to active relationship and organization. Both reads and mutation receipt replays reauthorize. Pagination uses actor/scope/revision-bound signed cursors. Message timestamps come from the backend. Page order is stable document-ID order, displayed chronologically within loaded records. No companion content is queried, imported or auto-inserted. User-authored message prose is not a semantic censorship mechanism.
- Appointment transitions: patient requests; psychologist proposes future start/end; patient confirms the exact revision; psychologist completes after end; psychologist rejects requested/proposed; either cancels requested/proposed/confirmed. Terminal appointments never reopen. Rescheduling is explicitly cancellation followed by a new patient request, not an atomic replacement. No availability/double-booking guarantee. Concurrent revisions conflict.
- Message, application and appointment notifications are transactionally generated with deterministic IDs and safe references only. Assignment records are durable assignment events; first-page inbox refresh materializes missing assignment notifications, in scoped pages of at most 200, without increasing a bulk assignment beyond Firestore's write limit. This is request-driven delivery, not an always-on worker. At most 10,000 assignment source records per refresh; beyond this the service returns unavailable instead of a false complete inbox. Read acknowledgements preserve their initial read timestamp. Unread counts in UI describe loaded notifications, not a global counter. Inbox refresh is manual; external push is absent.
- Submission updates live in professional_notifications and a separate professional-only route/schema. They contain only a submission reference and timestamp, not scores, interpretations or provider states. They are an activity feed without read receipts. Patient inbox routes cannot access this collection.
- Analytics run scoped, bounded complete scans in a transaction, grouping immutable versions and counting authoritative submissions once per attempt. `enrolled` means assignment count (repeat assignments count separately), not unique people. Current manual custom forms have `scoring_version=not_applicable`, never a clinical score. Up to 10,000 source rows, 1,000 versions and 200 daily points per version; above bounds returns unavailable, never truncated totals. Date filters operate on returned UTC daily counts; all-time totals are labelled. Future scored instruments require grouping by actual scoring version before enablement.
- Closed relationships retain professional history. Archival is separate owner-only metadata and requires a closed relationship; restoring metadata cannot reopen access or change identity. History pagination remains organization and relationship scoped. The roster labels loaded counts and offers active/closed filters; archival is visible in patient details.
- New writes remain backend-only. No production rules, deployment, external provider or Flutter source changes. No registration/migration implementation added.
